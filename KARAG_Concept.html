4Два плана: знания и данныеTwo planes: knowledge and data

В системе сознательно разделены два механизма. Их смешение — главная причина, по которой подобные продукты «уверенно врут».

The system deliberately separates two mechanisms. Blurring them is the main reason such products "confidently lie".

ПланPlaneС чем работаетWorks withПример вопросаExample questionМеханизмMechanism
ЗнанияKnowledgeТекст: регламенты, SOP, договорыText: policies, SOPs, contracts«Что говорит политика о возвратах?»"What does the returns policy say?"RAG — поиск фрагмента, ответ со ссылкойRAG — retrieve passage, answer with source
ДанныеDataСтруктурированные: 1Ф, ERP, БДStructured: 1F, ERP, databases«Сколько продали вчера?»"How much did we sell yesterday?"Запрос через «навык» (view или API)Query via a "skill" (view or API)
Ключевое правило.Key rule. RAG извлекает текст — он не считает суммы. На вопрос «продажи вчера» документный RAG выдаст правдоподобное, но неверное число. План данных строится отдельно — на проверенных запросах.RAG retrieves text — it does not compute totals. Ask document-RAG "yesterday's sales" and it returns a plausible but wrong number. The data plane is built separately, on verified queries.

5«Навыки» — ядро продукта"Skills" — the core of the product

Центральная абстракция — навык (по аналогии со «skills» у Claude): подготовленный, параметризованный запрос или отчёт, который технический специалист создаёт и тестирует один раз, после чего им пользуются все. Навык гарантирует корректность, потому что запрос написал и проверил человек.

The central abstraction is the skill (like Claude's "skills"): a prepared, parameterised query or report that a technical specialist builds and tests once, after which everyone uses it. A skill guarantees correctness because a human wrote and tested the query.

  • Большинство вопросов руководителей решаются навыком, а не импровизированным SQL.
  • Навык — универсальный «переходник»: внутри это либо SQL к view, либо вызов API. ИИ видит каталог безопасных навыков, а не «сырую» БД.
  • Свободные вопросы разрешены, но в рамках и всегда с показом выполненного запроса.
  • Most manager questions resolve to a skill, not improvised SQL.
  • A skill is a universal adapter: inside it's either SQL on a view or an API call. The AI sees a catalogue of safe skills, never the raw database.
  • Free-form questions are allowed, but within bounds and always showing the executed query.
Почему сильно.Why it's powerful. Навык решает сразу точность (проверено), безопасность (нет произвольного доступа к БД) и самообслуживание (навыки переиспользуются).A skill solves accuracy (verified), security (no arbitrary DB access) and self-service (skills are reused) all at once.

7Модель доступа (RBAC)Access model (RBAC)

Требование «CEO видит всё, но HR никогда не видит финансы» — самое строгое в продукте. Слово «никогда» требует доступа с учётом прав на этапе поиска, а не просто ролей при входе.

"The CEO sees everything, but HR never sees financials" is the strictest requirement in the product. "Never" demands permission-aware access at retrieval time, not just login roles.

Модель: матрица «роли × классы данных», по умолчанию запретModel: a roles × data-classes matrix, default-deny

  1. Каждый документ и источник классифицируется при загрузке: public / operational / HR / financial / regulated. Без класса — ограничен (fail-closed).
  2. Роли сопоставлены с классами. HR → {HR, operational, public}, без {financial}.
  3. Контроль в двух местах: при поиске (финансовый документ невидим для HR) и на уровне навыка.
  4. CEO = суперпользователь только своего арендатора, но не данных других компаний.
  5. Классификация: админ — на источник; загрузчик — на документ; авто-классификация — лишь подсказка.
  1. Every document and source is classified at upload: public / operational / HR / financial / regulated. Unclassified = restricted (fail-closed).
  2. Roles map to classes. HR → {HR, operational, public}, without {financial}.
  3. Enforced in two places: at retrieval (a financial doc is invisible to HR) and at the skill level.
  4. The CEO is a superuser of their own tenant only, never other companies' data.
  5. Classification: admin per source; uploader per document; auto-classification only as a suggestion.
Ловушка.The trap. Нельзя фильтровать ответ после поиска («модель видела, но ей сказали не говорить») — это утечка. Запрещённый контент не должен попадать в контекст вообще.You can't filter the answer after retrieval ("the model saw it but was told not to tell") — that leaks. Forbidden content must never enter the context at all.

9Размещение и LLMHosting and the LLM

Размещение: в собственном дата-центре KIT. Данные компании поступают в ДЦ KIT; для генерации ответа результат отправляется в LLM. Модель — сменная, по фазам:

Hosting: in KIT's own data centre. Company data comes to KIT's DC; to generate an answer, the result is sent to the LLM. The model is swappable, in phases:

Фаза 1 — LLM через APIPhase 1 — LLM via API

GigaChat для чувствительного контура (рос. серверы), OpenAI — для нечувствительного. Работает на текущем оборудовании KIT без GPU.GigaChat for the sensitive contour (Russian servers), OpenAI for non-sensitive. Runs on KIT's current hardware without a GPU.

Фаза 2 — свои GPUPhase 2 — own GPUs

GPU-узел для полностью локального вывода — когда у компании требование «никаких внешних сервисов» или счёт за API превысит стоимость GPU.A GPU node for fully local inference — when a company requires "no external services" or the API bill exceeds the cost of a GPU.
Честная граница.An honest boundary. Без GPU полностью локального вывода нет: для каждого ответа результат уходит во внешний API. Самых строгих заказчиков обслуживаем после установки GPU (Фаза 2). Для большинства ранних случаев GigaChat приемлем.Without a GPU there is no fully local inference: for every answer the result goes to an external API. The strictest customers are served only after a GPU (Phase 2). For most early cases GigaChat is acceptable.

16Ожидаемые вопросыAnticipated questions

Зачем своё, если есть ChatGPT / Glean?Why build our own when ChatGPT / Glean exist?
Данные в стране и в нашем периметре, дешевле, под нашим контролем, рус./тадж. язык, и в одном продукте — знания + живые данные + документы. Глобальные сервисы этого здесь не дают.Data stays in-country and in our perimeter, cheaper, under our control, RU/TJ language, and one product combines knowledge + live data + documents. Global services don't offer this here.
Безопасно ли? Не утечёт ли между компаниями?Is it secure? Could data leak between companies?
Жёсткая изоляция, доступ по умолчанию-запрет, только чтение, аудит. Чувствительное — через GigaChat/локально. Изоляцию проверяем до подключения регулируемых данных.Hard isolation, default-deny access, read-only, audit. Sensitive data via GigaChat/local. We test isolation before connecting regulated data.
А если ИИ выдаст неверную цифру?What if the AI gives a wrong number?
Частые вопросы решаются «навыками» — проверенными запросами. ИИ показывает источник и сам запрос. Последнее слово за человеком.Frequent questions resolve to "skills" — verified queries. The AI shows the source and the query itself. The human has the final word.
Сколько стоит и какие ресурсы?What's the cost and resources?
Фаза 1 — на текущем сервере KIT, LLM по API. GPU покупаем только когда заказчик потребует или счёт за API превысит стоимость GPU.Phase 1 runs on KIT's current server, LLM via API. We buy a GPU only when a customer requires it or the API bill exceeds the GPU cost.
Заменит ли это сотрудников?Will it replace employees?
Нет. ИИ усиливает людей. Урок рынка (Klarna): лучшие результаты — в связке «ИИ + человек».No. AI augments people. Market lesson (Klarna): the best results come from "AI + human" together.
Что если не взлетит?What if it doesn't take off?
Пилот с критериями успеха и остановки на малых вложениях. По итогам — «масштабировать / доработать / остановить». Риск ограничен.A pilot with success and stop criteria on a small budget. At the end — "scale / improve / stop". Risk is limited.

17Модель продажBusiness model

  • Внедрение / онбординг — разовая услуга (настройка данных, views, навыки).
  • Подписка — за компанию и/или за пользователя.
  • Потребление — по объёму запросов к LLM.
  • Премиум — локальный вывод на GPU (Фаза 2).
  • Implementation / onboarding — one-off service (data setup, views, skills).
  • Subscription — per company and/or per user.
  • Usage — by volume of LLM queries.
  • Premium — local GPU inference (Phase 2).
Стратегическая заметка.Strategic note. Продажа вовне делает KIT SaaS-вендором (поддержка, SLA, биллинг). Сначала отточить внутри группы (Фаза 0–1), затем выходить вовне.Selling externally makes KIT a SaaS vendor (support, SLA, billing). First refine inside the group (Phase 0–1), then go external.
